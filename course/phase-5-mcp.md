## Урок 5.1. Протокол MCP: JSON-RPC и дисциплина stdout

**Цель:** ученик понимает, как устроен MCP (Model Context Protocol — открытый протокол подключения инструментов и данных к ИИ-клиентам) на уровне сообщений, и может прочитать сырой обмен клиент↔сервер.
**До урока:** фаза 4 завершена (помощник v1.0); ничего нового ставить не нужно.
**Темы:**
- Зачем MCP: инструмент пишется один раз и работает в любом клиенте; отличие от tool use внутри одного приложения (4.4)
- Роли: хост, клиент, сервер; что сервер отдаёт — инструменты, ресурсы, промты (в этой фазе — только инструменты)
- JSON-RPC 2.0 — формат сообщений: request (id, method, params), response (result/error), notification без id
- Жизненный цикл: initialize → initialized → tools/list → tools/call
- Транспорт stdio: сервер читает stdin, пишет в stdout; ЖЕЛЕЗНОЕ правило — в stdout только протокол, любой print ломает канал, отладка только в stderr
**Материалы:** modelcontextprotocol.io — разделы Concepts (architecture, tools, transports) и Specification (базовый протокол, lifecycle); aiefs, урок 13.07 (MCP) — как обзор.
**Ход сессии:**
1. Разбор: схема хост–клиент–сервер; чем MCP-инструмент отличается от инструмента из tools.py урока 4.4.
2. Ученик руками пишет в файл `docs/mcp-trace.md` полный обмен для вымышленного инструмента ping: initialize → initialized → tools/list → tools/call — каждое сообщение как JSON.
3. Проверка: репетитор шлёт «сломанные» сообщения (без id, с print-мусором в потоке) — ученик объясняет, что сломается и почему.
4. Ученик пишет мини-скрипт `jsonrpc_echo.py`: читает JSON-RPC-строки из stdin, отвечает в stdout, весь лог — в stderr; проверка руками через echo и конвейер.
5. Обсуждение: почему print в stdout — главная причина «сервер не отвечает» и как это ловить (мост к 5.4).
**Задание:** `docs/mcp-trace.md` с полным жизненным циклом сообщений, выписанным руками; `jsonrpc_echo.py`, который корректно отвечает на request с id, молчит на notification и пишет отладку только в stderr.
**Артефакт:** mcp-trace.md — шпаргалка протокола, по ней ученик отлаживает сервер в 5.2–5.4; jsonrpc_echo.py — учебная проба stdio-дисциплины.
**Критерий готовности:** `echo '{"jsonrpc":"2.0","id":1,"method":"ping"}' | python jsonrpc_echo.py 2>/dev/null` возвращает ровно один валидный JSON-response и ничего больше; ученик без подглядывания называет Клоду порядок сообщений жизненного цикла MCP.

## Урок 5.4. Мост WSL↔Windows: подключение к Claude Code

**Цель:** ученик подключает ch-mcp, живущий в WSL, к Claude Code на Windows — и умеет диагностировать каждое звено моста, когда что-то молчит.
**До урока:** урок 5.3 (ch-mcp работает в инспекторе внутри WSL).
**Темы:**
- Анатомия моста: Claude Code (Windows) запускает процесс `wsl.exe -e ...` → внутри WSL стартует Python-сервер → stdio-канал прозрачно тянется через границу систем
- Конфиг `.mcp.json` в корне проекта: command="wsl.exe", args=["-e", "bash", "-lc", "..."] — почему нужен bash -lc (иначе не подхватятся настройки оболочки и PATH; сервер запускаем через `.venv/bin/python` из окружения, созданного uv) и почему путь к серверу внутри WSL пишется как ~/… , а не \\wsl$\…
- Переменные окружения: env в .mcp.json задаёт окружение для wsl.exe на стороне Windows и НЕ переезжает внутрь WSL автоматически — секреты грузим внутри: .env читает сам сервер (python-dotenv из 2.16) по абсолютному пути
- Типовые поломки, по одной на каждое звено: wsl.exe не найден / не тот дистрибутив (`wsl -l -v`); bash без -lc → «python not found»; относительный путь → сервер стартует не из той папки и не находит .env; print в stdout → клиент виснет на initialize; CRLF-концы строк в скриптах, правленных с Windows
- Отладка по слоям: сначала команда из .mcp.json руками в PowerShell → потом `claude mcp list` и лог Claude Code (`claude --mcp-debug`) → потом stderr сервера в файл
**Материалы:** modelcontextprotocol.io — Connect to local MCP servers (конфиг клиентов); docs.anthropic.com — Claude Code, раздел MCP; объяснение репетитора (мост WSL↔Windows — специфика среды ученика, во внешних курсах его нет).
**Ход сессии:**
1. Разбор: схема моста на бумаге — три звена (Windows-процесс, граница wsl.exe, Linux-процесс) и что может сломаться в каждом.

3. Ученик пишет `.mcp.json` в проекте, где работает Claude Code на Windows; перезапуск Claude Code, проверка `claude mcp list` и `/mcp`.
