# Фаза 4. Первый агент (10 уроков)

**Действующий инженерный контракт фазы:** внешние payload проходят Pydantic v2-валидацию до business logic; production допускает только заранее одобренные параметризованные SELECT с readonly-ролью и серверными лимитами времени, чтения, результата и памяти. `LIMIT` ограничивает выдачу, но не стоимость. В логах только redacted template id/hash, `query_id`, длительность и объёмы — без сырого SQL, параметров, secrets и PII. CI работает offline с network guard и без секретов. Retry не универсален: только идемпотентная стадия, retryable outcome и общий budget. Публикация, tag, commit и push условны и требуют отдельного явного разрешения; локальные evidence достаточны.

Цель фазы: собрать руками работающего ИИ-агента — программу, которая через API Anthropic вызывает модель, а модель через инструменты вызывает твой код.
На выходе ученик умеет: вызывать Claude из Python, писать и отлаживать промты, получать структурированные ответы, описывать инструменты, вести цикл агента, ограждать доступ к проду и проверять агента тестами.
Главный артефакт фазы: **помощник CRM-маркетолога v1.0** — агент с командной строкой, который по вопросу на русском строит безопасный SQL к ClickHouse и возвращает сводку по сегменту.
Артефакт переиспользуется дальше: инструменты уходят в MCP-сервер (фаза 5), к агенту подключается база знаний (урок 6.9), eval-каркас вырастает в полноценные эвалы (фаза 7), проект оформляется как кейс портфолио (фаза 8).
Опора на прошлые фазы: шаблон проекта (2.1), `crm_tools.transport.Transport` и `RetryPolicy` (2.10), `crm_tools.ch_client.ClickHouseClient` (2.11), тесты и заглушки (2.13–2.14), логирование и .env (2.16), CI (2.17), карта классов agent.py (2.23), sql_templates (3.4).

## Урок 4.1. Anthropic API: первый вызов

**Цель:** ученик из своего кода в WSL получает первый ответ от Claude через Messages API и понимает, из чего состоят запрос и ответ.
**До урока:** фазы 1–3 завершены; в WSL создан новый проект `crm-agent` по шаблону из 2.1 (окружение на uv, git, .env.example, pytest, ruff); получен ключ API Anthropic.
**Темы:**
- Messages API: что уходит в запрос (model, max_tokens, messages) и что приходит в ответ (content, stop_reason, usage)
- Роли в messages: user и assistant; system — отдельный параметр, а не роль
- Ключ API: только в .env, чтение через переменную окружения, `.env.example` в репозитории
- Токены и стоимость: usage в ответе, счёт входных и выходных токенов, зачем max_tokens
- Ошибки API: 401 (ключ), 429 (превышение частоты), 529 (перегрузка) — и как их читать
**Материалы:** anthropics/courses, курс anthropic_api_fundamentals: ноутбуки 01_getting_started, 02_messages_format, 04_parameters; docs.anthropic.com — справка Messages API.
**Ход сессии:**
1. Разбор: устройство запроса и ответа Messages API, роли, где живёт system.
2. Ученик руками ставит SDK `anthropic` через uv, заводит ключ в .env, пишет модуль `src/crm_agent/llm.py` с функцией `ask(prompt: str) -> str`.
3. Запуск из терминала WSL: три разных вопроса, разбор ответов и поля usage.
4. Ученик добавляет вывод стоимости вызова (токены из usage × тариф модели) и обработку ошибки при отсутствии ключа.
5. Обсуждение: чем вызов API отличается от чата в браузере (нет памяти между вызовами — история собирается тобой).
**Задание:** в установленном editable-пакете проекта `crm-agent` написать `src/crm_agent/llm.py`: функция `ask()` с параметрами model и max_tokens, чтение ключа из .env, печать usage после каждого вызова, понятная ошибка при пустом ключе. Модуль-проба `src/crm_agent/probe.py` задаёт вопрос из аргумента командной строки.
**Артефакт:** модуль `llm.py` — единая точка вызова модели; используется во всех уроках фазы 4 и в eval-каркасе 4.7.
**Критерий готовности:** `uv run python -m crm_agent.probe "Что такое RFM-сегментация?"` печатает ответ модели и число токенов; при удалённом ключе — понятное сообщение, а не трейс; импорт идёт из установленного `crm_agent`, а `src` не используется как имя пакета; ключ отсутствует в отслеживаемых файлах и локальном diff.

## Урок 4.3. Структурированные выводы

**Цель:** ученик получает от модели не прозу, а разбираемый программой JSON заданной схемы — и умеет валидировать и чинить его.
**До урока:** уроки 4.1–4.2 и 2.12a (llm.py, prompts.py; Pydantic v2 и проверка внешних данных).
**Темы:**
- Зачем структура: ответ модели как вход для кода, а не для глаз
- Способы добиться JSON: явная схема в промте, префилл (заготовка начала ответа за ассистента), stop-последовательности
- Разбор ответа: json.loads, типичные поломки (текст вокруг JSON, кавычки, запятые)
- Валидация схемы: Pydantic v2-модель `SegmentSpec` — поля сегмента (фильтры, период, метрики)
- Runtime-валидация выполняется до бизнес-логики: отдельно различаются синтаксически битый JSON и валидный JSON с неверными значениями; повтор допустим один раз только для безопасного чтения модели и не превращается в универсальную retry-политику
**Материалы:** anthropics/courses, tool_use: ноутбук 03_structured_outputs; prompt_engineering_interactive_tutorial, глава 5 (Formatting Output); docs.anthropic.com — префилл ответа ассистента.
**Ход сессии:**
1. Разбор: почему «просто попроси JSON» ломается и какие есть рычаги.
2. Ученик описывает схему `SegmentSpec` (Pydantic v2 из 2.12a) и промт, требующий строго JSON.
3. Запуск на пяти формулировках сегментов; разбор случаев, где JSON сломан.
4. Ученик пишет `parse_or_retry()`: разбор → при ошибке один повтор с текстом ошибки → исключение.
5. Обсуждение: структурированный вывод — это контракт между моделью и кодом; в 4.4 контрактом станет схема инструмента.

Тест в pytest на разбор эталонного JSON и на поведение при мусорном ответе (модель заглушена — приём из 2.14).
**Артефакт:** `structured.py` со схемой SegmentSpec — по этой схеме агент в 4.6 строит параметры для sql_templates; тесты пополняют каркас 4.7.

## Урок 4.7a. Типизированные порты и композиция агента

**Цель:** ученик отделяет ядро `crm_agent` от SDK и инфраструктуры, выражает границы через `Protocol`, собирает зависимости в одной точке и доказывает одинаковое поведение с детерминированными заглушками и реальными адаптерами.
**До урока:** обязательные уроки 2.12, 2.12a, 2.14 и 4.7; `Protocol` и сужение типов введены в 2.12, Pydantic v2 — в 2.12a, стратегия заглушек — в 2.14. Урок 5.6 и фаза 6 не требуются: `Retriever` здесь проектируется как будущий порт и проверяется заглушкой.

Агентное ядро быстро обрастает глобальными клиентами, условными импортами и словарями `Any`. Тогда тест с fake проходит по другому пути, чем рабочий запуск, а замена Anthropic, MCP или RAG затрагивает бизнес-логику. Порт описывает минимальное поведение, которое нужно ядру; адаптер переводит конкретный SDK в этот контракт; composition root создаёт config и ресурсы и передаёт их внутрь. Эта направленность зависимостей делает замену проверяемой без DI-фреймворка.

`Protocol` проверяет структурную совместимость статически и сам по себе не валидирует JSON во время выполнения. Поэтому внешние payload сначала проходят Pydantic-модель из 2.12a, а внутри ядра используются типизированные варианты результата. Состояния `ok`, `error`, `needs_confirmation` должны быть явными и исчерпывающе обработанными: отсутствие ветки обнаруживает type checker или негативный тест до запроса в ClickHouse.

**Темы:**
- порты `LLMClient`, `Tool`, `Retriever`, `TraceSink`; минимальные методы без утечки типов SDK;
- `Literal`/union для `ok | error | needs_confirmation`, сужение типа и запрет необоснованного `Any`;
- адаптеры Anthropic, ClickHouse/MCP и будущего RAG; runtime-валидация payload до ядра;
- composition root: типизированный config и клиенты создаются в точке входа, ресурсы имеют явного владельца;
- explicit injection против глобального singleton и `monkeypatch`; один core с fake и real/local adapter;
- проверка графа импортов: domain/application не импортируют SDK-адаптеры.
**Материалы:**
- Python 3.14, `typing`: разделы «Nominal vs structural subtyping» и `Protocol` — https://docs.python.org/3.14/library/typing.html#typing.Protocol
- Python typing specification: раздел «Protocols» — https://typing.python.org/en/latest/spec/protocol.html
- Pydantic v2: разделы «Models» и «Strict mode» — https://docs.pydantic.dev/latest/concepts/models/ и https://docs.pydantic.dev/latest/concepts/strict_mode/

**Ход сессии:**
1. Наставник на текущем `agent_core` объясняет направление зависимостей и показывает цельный путь `validated payload → port → adapter`; затем пауза для вопросов.
2. Ученик выписывает минимальные операции четырёх портов и самостоятельно типизирует три результата инструмента. Type checker должен отвергнуть намеренно несовместимый fake и пропущенное состояние.
3. Ученик переносит создание config, клиентов и registry в composition root, убирает глобальные клиенты и условные импорты из core. Сетевые вызовы на этом шаге запрещены.
4. Один сценарный тест 4.7 запускает тот же core с deterministic fakes. Отдельный локальный contract test запускает один разрешённый адаптер; production-вызов не нужен.
5. Ученик сравнивает explicit injection и прежний `monkeypatch`, объясняет границы каждого подхода и показывает отсутствие циклических импортов.
