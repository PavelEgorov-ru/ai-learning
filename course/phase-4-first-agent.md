# Фаза 4. Первый агент (9 уроков)

Цель фазы: собрать руками работающего ИИ-агента — программу, которая через API Anthropic вызывает модель, а модель через инструменты вызывает твой код.
На выходе ученик умеет: вызывать Claude из Python, писать и отлаживать промты, получать структурированные ответы, описывать инструменты, вести цикл агента, ограждать доступ к проду и проверять агента тестами.
Главный артефакт фазы: **помощник CRM-маркетолога v1.0** — агент с командной строкой, который по вопросу на русском строит безопасный SQL к ClickHouse и возвращает сводку по сегменту.
Артефакт переиспользуется дальше: инструменты уходят в MCP-сервер (фаза 5), к агенту подключается база знаний (урок 6.9), eval-каркас вырастает в полноценные эвалы (фаза 7), проект оформляется как кейс портфолио (фаза 8).
Опора на прошлые фазы: шаблон проекта (2.1), http_utils (2.10), ch_client (2.11), тесты и заглушки (2.13–2.14), логирование и .env (2.16), CI (2.17), карта классов agent.py (2.19), sql_templates (3.4).

## Урок 4.1. Anthropic API: первый вызов

**Цель:** ученик из своего кода в WSL получает первый ответ от Claude через Messages API и понимает, из чего состоят запрос и ответ.
**До урока:** фазы 1–3 завершены; в WSL создан новый проект `crm-agent` по шаблону из 2.1 (окружение на uv, git, .env.example, pytest, ruff); получен ключ API Anthropic.
**Темы:**
- Messages API: что уходит в запрос (model, max_tokens, messages) и что приходит в ответ (content, stop_reason, usage)
- Роли в messages: user и assistant; system — отдельный параметр, а не роль
- Ключ API: только в .env, чтение через переменную окружения, `.env.example` в репозитории
- Токены и стоимость: usage в ответе, счёт входных и выходных токенов, зачем max_tokens
- Ошибки API: 401 (ключ), 429 (превышение частоты), 529 (перегрузка) — и как их читать
**Материалы:** anthropics/courses, курс anthropic_api_fundamentals: ноутбуки 01_getting_started, 02_messages_format, 04_parameters; docs.anthropic.com — справка Messages API.
**Ход сессии:**
1. Разбор: устройство запроса и ответа Messages API, роли, где живёт system.
2. Ученик руками ставит SDK `anthropic` через uv, заводит ключ в .env, пишет модуль `llm.py` с функцией `ask(prompt: str) -> str`.
3. Запуск из терминала WSL: три разных вопроса, разбор ответов и поля usage.
4. Ученик добавляет вывод стоимости вызова (токены из usage × тариф модели) и обработку ошибки при отсутствии ключа.
5. Обсуждение: чем вызов API отличается от чата в браузере (нет памяти между вызовами — история собирается тобой).
**Задание:** в проекте `crm-agent` написать `llm.py`: функция `ask()` с параметрами model и max_tokens, чтение ключа из .env, печать usage после каждого вызова, понятная ошибка при пустом ключе. Скрипт-проба `probe.py`, который задаёт вопрос из аргумента командной строки.
**Артефакт:** модуль `llm.py` — единая точка вызова модели; используется во всех уроках фазы 4 и в eval-каркасе 4.7.
**Критерий готовности:** `python probe.py "Что такое RFM-сегментация?"` печатает ответ модели и число токенов; при удалённом ключе — понятное сообщение, а не трейс; ключа нет в git (`git log -p | grep -i api_key` пуст).

## Урок 4.2. Промптинг

**Цель:** ученик пишет промты, которые дают предсказуемый результат на CRM-задачах, и умеет чинить промт итерациями, а не наугад.

**Темы:**

- Разделение данных и инструкций: XML-теги для вставки пользовательского текста и данных
- Примеры в промте (few-shot — «обучение на примерах внутри промта»): 2–3 примера вход→выход

## Урок 4.3. Структурированные выводы

**Цель:** ученик получает от модели не прозу, а разбираемый программой JSON заданной схемы — и умеет валидировать и чинить его.
**До урока:** уроки 4.1–4.2 (llm.py, prompts.py).
**Темы:**
- Зачем структура: ответ модели как вход для кода, а не для глаз
- Способы добиться JSON: явная схема в промте, префилл (заготовка начала ответа за ассистента), stop-последовательности
- Разбор ответа: json.loads, типичные поломки (текст вокруг JSON, кавычки, запятые)
- Валидация схемы: dataclass/pydantic-модель `SegmentSpec` — поля сегмента (фильтры, период, метрики)
- Повтор при невалидном ответе: один повторный запрос с текстом ошибки
**Материалы:** anthropics/courses, tool_use: ноутбук 03_structured_outputs; prompt_engineering_interactive_tutorial, глава 5 (Formatting Output); docs.anthropic.com — префилл ответа ассистента.
**Ход сессии:**
1. Разбор: почему «просто попроси JSON» ломается и какие есть рычаги.
2. Ученик описывает схему `SegmentSpec` (dataclass из 2.7 или pydantic из 2.12) и промт, требующий строго JSON.
3. Запуск на пяти формулировках сегментов; разбор случаев, где JSON сломан.
4. Ученик пишет `parse_or_retry()`: разбор → при ошибке один повтор с текстом ошибки → исключение.
5. Обсуждение: структурированный вывод — это контракт между моделью и кодом; в 4.4 контрактом станет схема инструмента.
**Задание:** модуль `structured.py`: `SegmentSpec` + функция `extract_segment_spec(text) -> SegmentSpec`, которая по описанию сегмента на русском возвращает валидный объект (фильтры, период, метрика). Тест в pytest на разбор эталонного JSON и на поведение при мусорном ответе (модель заглушена — приём из 2.14).
**Артефакт:** `structured.py` со схемой SegmentSpec — по этой схеме агент в 4.6 строит параметры для sql_templates; тесты пополняют каркас 4.7.
**Критерий готовности:** `pytest tests/test_structured.py` зелёный; живой прогон на пяти формулировках даёт пять валидных SegmentSpec (допустим один повтор на формулировку).

## Урок 4.4. Tool use: модель вызывает мой код

## Урок 4.6. Инструмент ClickHouse и ограждения

**Цель:** ученик подключает агенту доступ к прод-ClickHouse через безопасный инструмент: только шаблонные запросы, лимиты, подтверждение человеком, без персональных данных в модели.
**До урока:** урок 4.5; работающие ch_client (2.11) и sql_templates (3.4).
**Темы:**
- Инструмент get_segment: аргументы = параметры шаблона из sql_templates, никакого сырого SQL от модели
- Ограждения по умолчанию: LIMIT, ограничение периода, max_execution_time, только чтение
- Показ широкого запроса человеку: если параметры выходят за пороги (период, ожидаемый объём) — инструмент возвращает SQL на подтверждение, а не выполняет его
- Обезличивание: почты/телефоны не попадают в tool_result — в модель только агрегаты и счётчики, выгрузка строк в файл
- Лог каждого SQL: кто, когда, какой запрос, сколько строк (задел под JSONL в 4.9)
**Материалы:** объяснение репетитора; свои артефакты — ch_client (урок 2.11) и sql_templates (урок 3.4); clickhouse.com/docs — настройки readonly и max_execution_time.
**Ход сессии:**
1. Разбор: модель поворотов не выбирает — угроза не «злой ИИ», а широкий запрос в прод и утечка персональных данных в контекст.
2. Ученик пишет `tools_ch.py`: инструмент get_segment поверх sql_templates + ch_client; схема аргументов из SegmentSpec (4.3).
3. Ученик добавляет пороги: широкий запрос → возврат `needs_confirmation` с текстом SQL; подтверждение — отдельным аргументом.
4. Запуск в агенте: «сколько клиентов не покупали 90 дней?» — проверка, что SQL шаблонный, LIMIT на месте, лог записан.
5. Обсуждение: проверка обезличивания — искусственный шаблон, возвращающий почты, должен отдать в модель только счётчик, строки — в файл.
**Ядро сессии:** шаги 1–3 — get_segment с ограждениями и needs_confirmation написан.
**Хвост, если не успели:** шаги 4–5 (живой прогон в агенте и проверка обезличивания) — доделка между сессиями; пока проверка обезличивания не пройдена, критерий готовности не закрыт и инструмент к живым вопросам не допускается.
**Задание:** `tools_ch.py`: get_segment (счёт и сводка по сегменту через шаблоны 3.4) с ограждениями: LIMIT и период по умолчанию, пороги с needs_confirmation, обезличивание tool_result, лог SQL в файл. Встроить в реестр агента, прогнать 3 живых вопроса из своей работы.
**Артефакт:** `tools_ch.py` — главный рабочий инструмент помощника v1.0; в 5.3 его логика переезжает в MCP-сервер ch-mcp почти без изменений.
**Критерий готовности:** на узком вопросе агент отвечает сам; на широком («все заказы за всё время») — показывает SQL и ждёт подтверждения; в логе есть все выполненные запросы; в переписке с моделью нет ни одной почты/телефона (ученик показывает распечатку Клоду).
**Промт для старта сессии:**

Прочитай:
1. ai-learning\course\00-overview.md — правила курса;
2. ai-learning\course\phase-4-first-agent.md — раздел урока 4.6;
3. ai-learning\course\journal.md — последние записи.
Веди сессию по файлу урока: разбор темы → я пишу код руками в WSL → проверяем запуском. Код за меня не пиши — подсказки, наводящие вопросы, разбор моих ошибок. В конце: квиз 5–7 вопросов по уроку (+1–2 на повторение из журнала), проверка критерия готовности, git-коммит артефактов урока, разбор моих вопросов за сессию (пробелы — кандидатами на мини-урок в журнал), запись результата в журнал.

## Урок 4.7. Мини-golden set и заглушки

**Цель:** ученик собирает эталонный набор задач (golden set — «золотой набор»: вход + ожидаемый результат) и прогоняет агента через pytest без сети и без прода.
**До урока:** уроки 4.5–4.6; навык заглушек из 2.14.
**Темы:**
- Golden set: 5–10 задач помощника — вопрос, ожидаемый инструмент, ожидаемые аргументы, признак хорошего ответа
- Детерминированная заглушка LLM: поддельный клиент, который на заданную историю возвращает заранее записанные ответы (в т.ч. блоки tool_use)
- Детерминированные заглушки инструментов: get_segment без сети, фиксированные данные
- Тест сценария целиком: agent_core + заглушки → проверка маршрута (какие инструменты, с какими аргументами) и финального ответа
- Что тестом не поймать: качество текста — остаётся живой прогон и глаза (мост к фазе 7)
**Материалы:** объяснение репетитора; Aiagentsfullcourse, текст модуля 09 (эвалы) — как конспект; свои тесты из уроков 2.13–2.14 как образец.
**Ход сессии:**
1. Разбор: зачем тестировать агента без модели — скорость, ноль стоимости, повторяемость; что такое golden set.
2. Ученик составляет `evals/golden.jsonl`: 5–10 задач из своей практики с ожиданиями.
3. Ученик пишет `tests/fakes.py`: FakeLLM (записанные ответы по шагам) и FakeGetSegment (фиксированные данные).
4. Ученик пишет `tests/test_agent_flow.py`: параметризованный тест по golden.jsonl — маршрут инструментов и проверка ответа.
5. Прогон `pytest`, разбор падений; обсуждение: заглушка фиксирует сегодняшний контракт — при смене промта тесты честно краснеют.
**Задание:** golden.jsonl (5–10 задач), fakes.py, test_agent_flow.py; все тесты зелёные и работают без ANTHROPIC_API_KEY и без доступа к ClickHouse (проверить, выключив сеть или убрав ключ). Подключить к CI из 2.17.
**Артефакт:** eval-каркас (golden.jsonl + fakes + тесты) — страховка при доводке 4.8–4.9; в 7.1–7.2 вырастает в golden set на 30–50 задач с метриками.
**Критерий готовности:** `pytest tests/test_agent_flow.py` зелёный при отсутствующем ключе API; в наборе не меньше 5 задач; CI на GitHub зелёный.

В конце: квиз 5–7 вопросов по уроку (+1–2 на повторение из журнала), проверка критерия готовности, git-коммит артефактов урока, разбор моих вопросов за сессию (пробелы — кандидатами на мини-урок в журнал), запись результата в журнал.

## Урок 4.8. Интеграция и CLI
