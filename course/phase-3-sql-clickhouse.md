# Фаза 3. SQL и ClickHouse (4 урока)

Цель фазы: научиться уверенно доставать из прод-ClickHouse (только чтение, HTTP-интерфейс) ответы на CRM-задачи — сегменты, когорты, RFM — с учётом особенности витрин: батчевый dbt хранит версии строками, поэтому «последнее состояние» всегда берётся через argMax или окна.
На выходе ученик: пишет с нуля запросы с агрегатами, JOIN, CTE и окнами; понимает, во что запрос обходится ClickHouse и как его удешевить; никогда не путает число строк с числом сущностей.
Главный артефакт фазы: тетрадь запросов `sql/tetrad-zaprosov.md` и модуль `sql_templates` — параметризованные безопасные шаблоны. sql_templates становится основой инструмента get_segment агента в уроке 4.6, а задачи из тетради — заготовками golden set в 4.7.
Сквозные правила фазы: только чтение; LIMIT и ограничение периода по умолчанию; лог каждого SQL; персональные данные (почты, телефоны) не попадают в контекст LLM и в тетрадь — выгрузки только в файл вне git, в обсуждение и в модель идут агрегаты или обезличенные примеры (client_id).

## Урок 3.1. SQL для CRM: агрегаты, даты, JOIN, CTE

**Цель:** писать с нуля запросы к прод-ClickHouse для типовых CRM-вопросов — с агрегатами, функциями дат, соединениями и CTE.
**До урока:** фаза 2 завершена: работает ch_client (2.11) с тестами (2.14), утилита segment (2.18); есть проверенный доступ к прод-ClickHouse через HTTP (readonly).
**Темы:**
- SELECT / WHERE / GROUP BY / ORDER BY; агрегаты count, sum, avg, uniqExact;
- функции дат: toDate, toStartOfMonth, toStartOfWeek, dateDiff, now() и интервалы;
- JOIN: LEFT и INNER, ключи соединения, типичная ошибка размножения строк;
- CTE (WITH — именованный подзапрос): читаемая сборка запроса по шагам;
- правила по умолчанию: LIMIT в каждом запросе, ограничение периода в WHERE, результат с почтами/телефонами — только в файл, в тетрадь и Клоду — агрегаты.

**Материалы:** clickhouse.com/docs — SQL Reference (SELECT, агрегатные функции, функции для работы с датами); объяснение репетитора.
**Ход сессии:**
1. Разбор: анатомия запроса, порядок выполнения секций, зачем CTE.
2. Ученик руками пишет запросы к своим витринам через ch_client/curl: от простого count по периоду до JOIN двух витрин и CTE.
3. Проверка запуском: каждый запрос выполняется на проде с LIMIT и периодом, результат сверяется со здравым смыслом («похоже ли на правду»).
4. Обсуждение: где JOIN размножил строки, какие вопросы из рабочих задач ученика ложатся на эти конструкции.

**Задание:** завести `sql/tetrad-zaprosov.md` и записать 8–10 запросов по своим рабочим CRM-вопросам в формате «задача → SQL → результат-агрегат → вывод»; каждый запрос обязан иметь LIMIT и ограничение периода; персональные поля в результаты не тянуть.
**Артефакт:** тетрадь запросов `sql/tetrad-zaprosov.md` — пополняется в 3.2–3.4, служит источником шаблонов для sql_templates (3.4) и задач для golden set (4.7).
**Критерий готовности:** ученик при репетиторе пишет с нуля и выполняет запрос «выручка по месяцам за последние N месяцев по заданному сегменту» без подсказок; во всех запросах тетради есть LIMIT и период.

## Урок 3.2. Специфика ClickHouse: MergeTree, стоимость, версии строк

**Цель:** понимать, как ClickHouse хранит и читает данные, во что обходится запрос, и правильно работать с витринами, где батчевый dbt хранит версии строками.
**До урока:** ничего, кроме предыдущего урока (тетрадь запросов начата).
**Темы:**
- MergeTree: колоночное хранение, куски (parts), почему строки не обновляются на месте;
- ключ сортировки и партиции: как WHERE по ним удешевляет запрос; PREWHERE;
- версии строк из батчевого dbt: одна сущность = много строк, total_rows и count() ≠ число сущностей; последнее состояние через argMax(поле, поле_версии);
- стоимость запроса: rows_read/bytes_read в ответе, чем плох SELECT *;
- ограждения: max_execution_time, readonly-режим — почему они всегда включены.

**Материалы:** clickhouse.com/docs — движок MergeTree, функция argMax, настройка max_execution_time; объяснение репетитора.
**Ход сессии:**
1. Разбор: как лежат данные в MergeTree и откуда в витринах берутся строки-версии.
2. Ученик руками сравнивает на своей витрине count(), uniqExact(id) и срез последнего состояния через argMax — три разных числа, объяснить каждое.
3. Руками: один и тот же запрос с фильтром по ключу партиции и без — сравнить rows_read; попробовать PREWHERE.
4. Проверка запуском: запрос с max_execution_time и заведомо тяжёлый запрос, который в него упирается.
5. Обсуждение: какие витрины ученика версионируются и по какому полю определять свежесть строки.

**Задание:** взять 3 своих рабочих витрины и для каждой записать в тетрадь: как хранятся версии (поле версии/даты обновления), count() против uniqExact(id), запрос «последнее состояние сущности» через argMax, разница чисел с объяснением; плюс один пример «дорогой против дешёвого» запроса с показаниями rows_read.
**Артефакт:** раздел тетради «мои витрины: версии и последнее состояние» — обязательная справка для паттернов в 3.3, шаблонов в 3.4 и инструмента агента в 4.6.
**Критерий готовности:** ученик объясняет Клоду своими словами, почему count() по витрине ≠ числу клиентов, и при нём пишет argMax-срез последнего состояния по любой из трёх витрин.

## Урок 3.3. Оконные функции и сегментные паттерны

**Цель:** применять оконные функции и собирать три опорных CRM-паттерна: RFM, когорты, последнее состояние.
**До урока:** уроки 3.1–3.2 (в тетради есть раздел про версии витрин).
**Темы:**
- оконные функции: OVER (PARTITION BY … ORDER BY …), row_number, ранги;
- «последнее состояние» через окно (row_number() = 1) против argMax — когда какой способ удобнее;
- RFM-сегментация: давность (recency), частота (frequency), деньги (monetary) — расчёт и разбиение на группы;
- когорты: месяц первой покупки, таблица удержания по месяцам;

**Материалы:** clickhouse.com/docs — оконные функции (Window Functions); объяснение репетитора.

## Урок 3.4. Безопасные шаблоны SQL для агента (sql_templates)

**Цель:** превратить проверенные запросы тетради в модуль sql_templates — параметризованные шаблоны с ограждениями, которые потом получит агент.
**До урока:** уроки 3.1–3.3 (тетрадь с паттернами), ch_client из 2.11 с тестами из 2.14.
**Темы:**
- почему агенту нельзя давать писать произвольный SQL: инъекции, дорогие запросы, утечка персональных данных;
- параметризованные запросы ClickHouse (query parameters) вместо подстановки строк;
- разрешительный список (allowlist) таблиц и полей; поля с почтами/телефонами в шаблоны не входят по построению;
- принудительные ограждения в каждом шаблоне: LIMIT, обязательный период, max_execution_time, readonly;
- лог каждого SQL: что, когда, с какими параметрами, сколько строк прочитано;
- тесты шаблонов на заглушке ch_client: правильная подстановка параметров, отказ на запрещённое поле.

**Материалы:** clickhouse.com/docs — параметризованные запросы (query parameters), настройки запроса; объяснение репетитора.
**Ход сессии:**
1. Разбор: угрозы произвольного SQL и архитектура «шаблон + параметры + ограждения».
2. Ученик руками пишет модуль `sql_templates.py` поверх ch_client: 4–6 шаблонов из тетради (сегмент по условию, RFM, последнее состояние через argMax, выручка по периодам).
3. Руками: лог каждого выполнения и проверки параметров (allowlist полей, обязательный период).
4. Проверка запуском: pytest на заглушках + один живой прогон каждого шаблона на проде с LIMIT.
5. Обсуждение: как этот модуль станет инструментом get_segment в 4.6 и что агент никогда не увидит (сырые почты, произвольные таблицы).

**Задание:** модуль `sql_templates.py` с 4–6 шаблонами из тетради: каждый принимает именованные параметры, сам подставляет LIMIT/период/max_execution_time, пишет лог SQL и не содержит полей с персональными данными; тесты: корректная подстановка параметров, отказ при запросе поля вне allowlist, отказ без периода.
**Артефакт:** `sql_templates.py` + тесты в репозитории. Основа инструмента get_segment агента (4.6) и MCP-сервера к ClickHouse (5.3); тетрадь запросов остаётся справочником.
**Критерий готовности:** pytest по sql_templates проходит; попытка запросить через шаблон поле email отклоняется с понятной ошибкой; живой прогон каждого шаблона возвращает агрегаты и пишет лог; коммит в конце сессии сделан.
