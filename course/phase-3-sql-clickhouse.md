# Фаза 3. SQL и ClickHouse (4 урока)

Цель фазы: научиться получать через SQL и HTTP-интерфейс ответы на CRM-задачи — сегменты, когорты, RFM. Основная практика идёт на синтетических данных, локальном стенде или заглушке. Production допускается только для заранее согласованных SELECT через разрешённые шаблоны. Если документация конкретной витрины подтверждает хранение версий отдельными строками, «последнее состояние» строится через `argMax` или окна по проверенному полю версии.
На выходе ученик: пишет с нуля запросы с агрегатами, JOIN, CTE и окнами; понимает, во что запрос обходится ClickHouse и как его удешевить; никогда не путает число строк с числом сущностей.
Главный артефакт фазы: тетрадь запросов `sql/tetrad-zaprosov.md` и модуль `sql_templates` — параметризованные безопасные шаблоны. sql_templates становится основой инструмента get_segment агента в уроке 4.6, а задачи из тетради — заготовками golden set в 4.7.
Сквозные правила фазы: production — только заранее согласованные SELECT через разрешённые параметризованные шаблоны, с подтверждёнными readonly-правами и серверными лимитами времени, памяти, чтения и результата. Период сужается заранее. `LIMIT` ограничивает результат, но сам по себе не ограничивает стоимость чтения, JOIN, сортировки или агрегации. Нет подтверждённой защиты или явного разрешения — использовать синтетические данные, локальный стенд либо заглушку и отметить production smoke как невыполненный. INSERT, DDL и любые проверки мутаций в production запрещены; негативные проверки выполняются только в одноразовой локальной/изолированной среде. В лог идут query/template ID, статус, длительность, объёмы и очищенное представление; сырой SQL с параметрами, ключи, почты и телефоны не логируются и не передаются LLM.

## Урок 3.1. SQL для CRM: агрегаты, даты, JOIN, CTE

**Цель:** писать с нуля запросы для типовых CRM-вопросов — с агрегатами, функциями дат, соединениями и CTE — и безопасно отделять локальную практику от разрешённого production SELECT.
**До урока:** фаза 2 завершена: работает `ch_client` (2.11) с тестами (2.14), утилита `segment` (2.18); для обязательной практики достаточно локального стенда или заглушки. Production-доступ используется только если отдельно подтверждены разрешение, readonly-права, разрешённые шаблоны и серверные лимиты.
**Темы:**
- SELECT / WHERE / GROUP BY / ORDER BY; агрегаты count, sum, avg, uniqExact;
- функции дат: toDate, toStartOfMonth, toStartOfWeek, dateDiff, now() и интервалы;
- JOIN: LEFT и INNER, ключи соединения, типичная ошибка размножения строк;
- CTE (WITH — именованный подзапрос): читаемая сборка запроса по шагам;
- правила по умолчанию: узкий период в `WHERE`, ограниченный результат и отдельные серверные лимиты стоимости; `LIMIT` не считать защитой от дорогого чтения. Почты и телефоны не выбирать для учебной практики; в тетрадь и LLM идут только синтетические или согласованные агрегированные примеры.

**Материалы:** clickhouse.com/docs — SQL Reference (SELECT, агрегатные функции, функции для работы с датами); объяснение репетитора.
**Ход сессии:**
1. Разбор: анатомия запроса, порядок выполнения секций, зачем CTE.
2. Ученик руками пишет запросы через `ch_client`/`curl` к синтетическому набору, локальному ClickHouse или заглушке: от простого `count` по периоду до JOIN двух таблиц и CTE. Если production-доступ отдельно разрешён и защищён, один заранее согласованный узкий SELECT выполняется как дополнительный smoke.
3. Проверка запуском: каждый запрос сначала выполняется в изолированном контуре; результат и объёмы чтения сверяются с ожидаемыми значениями. Production-smoke, если он разрешён, не заменяет локальную детерминированную проверку.
4. Обсуждение: где JOIN размножил строки, какие вопросы из рабочих задач ученика ложатся на эти конструкции.

**Задание:** завести `sql/tetrad-zaprosov.md` и записать 8–10 запросов по CRM-вопросам на синтетической схеме в формате «задача → SQL → ожидаемый агрегат → вывод»; у каждого запроса есть узкий период, ограниченный результат и объяснение, какие серверные лимиты сдерживают стоимость. Персональные поля в результаты не включать. Рабочие имена таблиц и внутренние цифры добавлять только после отдельной проверки чувствительности.

## Урок 3.2. Специфика ClickHouse: MergeTree, стоимость, версии строк

**Цель:** понимать, как ClickHouse хранит и читает данные, во что обходится запрос, и правильно работать с витринами, где батчевый dbt хранит версии строками.
**До урока:** ничего, кроме предыдущего урока (тетрадь запросов начата).
**Темы:**
- MergeTree: колоночное хранение, куски (parts), почему строки не обновляются на месте;
- ключ сортировки и партиции: как WHERE по ним удешевляет запрос; PREWHERE;
- версии строк из батчевого dbt, если этот контракт подтверждён схемой и документацией конкретной витрины: одна сущность может иметь много строк, `count()` может отличаться от числа сущностей; последнее состояние определяется по проверенному полю версии через `argMax`;
- стоимость запроса: `rows_read`/`bytes_read` в ответе, чем плох `SELECT *`, почему малый `LIMIT` не гарантирует дешёвый запрос;
- ограждения: readonly-права, `max_execution_time`, лимиты памяти, чтения и результата; клиентские timeout и узкий период дополняют, но не заменяют серверную защиту.

**Материалы:** clickhouse.com/docs — движок MergeTree, функция argMax, настройка max_execution_time; объяснение репетитора.
**Ход сессии:**
1. Разбор: как лежат данные в MergeTree и откуда в витринах берутся строки-версии.
2. На синтетической версионированной таблице ученик сравнивает `count()`, `uniqExact(id)` и срез последнего состояния через `argMax` — объясняет каждое число. Для рабочей витрины сначала читает схему/документацию и не переносит этот контракт по догадке.
3. В локальном или изолированном ClickHouse выполняет один запрос с фильтром по ключу партиции и без него, сравнивает `rows_read`, пробует `PREWHERE` и отдельно наблюдает, что `LIMIT` результата не гарантирует малого чтения.
4. Проверка таймаута и заведомо тяжёлого запроса проводится только на одноразовой локальной/изолированной таблице. В production намеренно тяжёлые запросы не запускаются.
5. Обсуждение: для каких витрин версионирование и поле свежести документированы, а где данных для вывода пока нет.

**Задание:** на синтетической таблице записать в тетрадь `count()` против `uniqExact(id)`, запрос последнего состояния через `argMax` и объяснение различий; добавить пример «дорогой против дешёвого» с `rows_read` из локального стенда. Для трёх рабочих витрин составить только проверенную по схеме/документации карточку: есть ли версии, какое поле определяет свежесть и разрешён ли учебный SELECT. Неизвестное пометить неизвестным, запросы не запускать без отдельного разрешения.
**Артефакт:** раздел тетради «мои витрины: версии и последнее состояние» — обязательная справка для паттернов в 3.3, шаблонов в 3.4 и инструмента агента в 4.6.
**Критерий готовности:** ученик объясняет своими словами, при каком подтверждённом контракте `count()` по витрине отличается от числа клиентов, и пишет/выполняет `argMax`-срез на синтетической версионированной таблице. Свойства production-витрины утверждаются только со ссылкой на её схему или документацию.

## Урок 3.4. Безопасные шаблоны SQL для агента (sql_templates)

**Цель:** превратить проверенные запросы тетради в модуль sql_templates — параметризованные шаблоны с ограждениями, которые потом получит агент.
**До урока:** уроки 3.1–3.3 (тетрадь с паттернами), ch_client из 2.11 с тестами из 2.14.
**Темы:**
- почему агенту нельзя давать писать произвольный SQL: инъекции, дорогие запросы, утечка персональных данных;
- параметризованные запросы ClickHouse (query parameters) вместо подстановки строк;
- разрешительный список (allowlist) таблиц и полей; поля с почтами/телефонами в шаблоны не входят по построению;
- принудительные ограждения в каждом шаблоне: разрешённый тип SELECT, обязательный узкий период, ограничение результата и подтверждённые серверные лимиты времени, памяти, чтения и результата;
- очищенный лог выполнения: query/template ID, статус, длительность, прочитанные/возвращённые строки и байты; без сырых параметров, PII, ключей и полного SQL с чувствительными литералами;
- тесты шаблонов на заглушке ch_client: правильная подстановка параметров, отказ на запрещённое поле.

**Материалы:** clickhouse.com/docs — параметризованные запросы (query parameters), настройки запроса; объяснение репетитора.
**Ход сессии:**
1. Разбор: угрозы произвольного SQL и архитектура «шаблон + параметры + ограждения».
2. Ученик руками пишет модуль `sql_templates.py` поверх ch_client: 4–6 шаблонов из тетради (сегмент по условию, RFM, последнее состояние через argMax, выручка по периодам).

Очищенный лог не раскрывает параметры и PII.
