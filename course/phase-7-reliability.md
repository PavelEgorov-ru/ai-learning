# Фаза 7. Надёжность и эксплуатация (11 уроков)

Цель фазы: превратить помощника CRM-маркетолога (4.9), ch-mcp (5.5) и RAG-агента (6.9) из «работает у меня» в сервис, которому можно доверять: измеримое качество, наблюдаемость, защита данных, понятная архитектура и эксплуатация по расписанию.
На выходе ученик умеет: собирать golden set и рубрику, гонять автоматические прогоны с порогом регрессии, калибровать LLM-судью, распараллеливать прогоны через asyncio, читать трейсы и считать стоимость, вычищать персональные данные, защищать агента слоем guardrails с проверкой каждого вызова инструмента до выполнения, описывать архитектуру схемой и ADR, упаковывать сервис и вести его по runbook.
Главный артефакт фазы: эксплуатационный контур помощника — golden set + eval-раннер + трейсы + redaction + runbook. Всё это станет доказательной базой кейсов в фазе 8 (тесты/эвалы, ограничения, скриншоты логов).

## Урок 7.2. Автопрогон, метрики и порог регрессии

**Цель:** ученик умеет автоматически прогонять golden set через помощника, считать метрики и ловить регрессию (ухудшение качества после изменения) по порогу.
**До урока:** golden_set.jsonl и rubrika.md (7.1); CI-шаблон из урока 2.17.
**Темы:**
- eval-раннер: прогон каждой задачи через помощника, сохранение ответа и вердикта в JSONL-отчёт
- какие проверки автоматизируются без LLM: точное совпадение чисел, наличие обязательных полей, «SQL выполнился без ошибки», «нет персональных данных в ответе»
- метрики: доля пройденных, разбивка по типам задач, доля отказов инструментов
- порог регрессии: базовая линия (baseline) фиксируется в файле, прогон падает, если метрика ниже порога
- стоимость прогона: почему на каждый чих полный набор не гоняют (подмножество smoke — быстрая проверка на 5–10 задачах)
**Материалы:** Aiagentsfullcourse, текст модуля 09 — конспект по метрикам; объяснение репетитора.

5. Обсуждение: как это встроится в CI (по образцу 2.17) и почему полный прогон — не на каждый коммит.
**Задание:** написать eval_runner.py с автоматическими проверками минимум трёх типов, сводкой метрик и порогом регрессии; зафиксировать baseline; включить smoke-подмножество (5–10 задач) в CI-конвейер репозитория помощника.

## Урок 7.3. LLM-судья: смещения и калибровка

**Цель:** ученик умеет подключать LLM-судью (модель, оценивающую ответы другой модели) для проверок, которые не автоматизируются кодом, и калибровать его по своим ручным оценкам.
**До урока:** ручная рубрика и ручные оценки из 7.1, eval_runner.py из 7.2 — судья подключается строго ПОСЛЕ того, как ученик сам оценивал руками и понимает, что такое «хороший ответ».
**Темы:**
- зачем судья: свободный текст («объясни сегмент») кодом не проверить, руками — долго
- смещения судьи: снисходительность (завышает оценки), любовь к многословию, позиционное смещение при сравнении пар, самопредпочтение (своим формулировкам)
- промт судьи из рубрики 7.1: критерии, шкала, требование объяснить вердикт до балла, примеры оценённых ответов
- калибровка: прогнать судью по ответам, уже оценённым вручную в 7.1, посчитать долю совпадений; где расходится — чинить промт судьи, а не переписывать свои оценки
- границы доверия: судья — сигнал для сортировки, спорные случаи всё равно смотрятся глазами
**Материалы:** anthropics/courses (github) — раздел про оценивание; Aiagentsfullcourse, текст модуля 09 — конспект; объяснение репетитора.
**Ход сессии:**

## Урок 7.4. asyncio и httpx: параллельный eval-раннер

**Цель:** ученик понимает событийный цикл asyncio и умеет распараллеливать сетевые вызовы, чтобы полный прогон golden set шёл минуты, а не час.
**До урока:** eval_runner.py с судьёй (7.2–7.3); http_utils из 2.10.
**Темы:**
- почему медленно: последовательные сетевые ожидания; конкурентность против параллельности на пальцах
- async/await и событийный цикл: одна нить, много одновременных ожиданий
- httpx.AsyncClient вместо requests; перенос привычек из http_utils (таймауты, повторы) в асинхронный код
- ограничение одновременности: asyncio.Semaphore, лимиты API (коды 429), почему «всё сразу» — плохо
- сбор результатов: asyncio.gather, обработка исключений отдельной задачи без падения всего прогона
**Материалы:** объяснение репетитора; документация httpx (официальный сайт, раздел Async).
**Ход сессии:**

## Урок 7.5. Наблюдаемость: JSONL-трейсы, correlation id, стоимость

**Цель:** ученик умеет по логам восстанавливать полный ход любого запроса к агенту и знает, во сколько обходится каждый запрос и день работы.
**До урока:** помощник v1.0 с JSONL-логами из 4.9; logging из 2.16.
**Темы:**
- трейс (запись хода выполнения): один запрос пользователя = цепочка событий (запрос → вызовы LLM → вызовы инструментов → ответ)
- correlation id (сквозной идентификатор запроса): генерация в точке входа, протаскивание через все слои, включая ch-mcp и RAG
- структура события: время, id, тип, длительность, входные токены, выходные токены, ошибка
- стоимость: токены из ответа API × тариф модели; сводка за день/неделю
- чтение трейсов: как за минуту найти, почему конкретный запрос ответил ерундой
**Материалы:** объяснение репетитора; документация Anthropic (docs.anthropic.com) — поля usage в ответе API; для кругозора (не для практики): NirDiamant/agents-towards-production, туториал tracing-with-langsmith — как трейсинг делают через SaaS-платформы; наш путь — локальные JSONL, и это осознанный выбор.
**Ход сессии:**
1. Разбор: чем трейс отличается от строкового лога «что-то случилось»; разбор пары реальных логов помощника из 4.9.
2. Ученик пишет tracer.py: контекст запроса с correlation id, функция записи события в trace.jsonl.
3. Ученик встраивает трейсер в agent_core и инструменты: каждый вызов LLM и каждый SQL — отдельное событие с токенами и длительностью.
4. Ученик пишет cost_report.py: сводка стоимости по дням и по типам событий из trace.jsonl.
5. Проверка чтением: репетитор называет «сломанный» запрос — ученик по трейсу находит, на каком шаге и что пошло не так.
**Задание:** встроить трейсер во все три сервиса (помощник, ch-mcp, RAG-агент — минимум в помощника и его инструменты), написать cost_report.py; прогнать eval-раннер и получить сводку стоимости прогона.
**Артефакт:** tracer.py + cost_report.py + формат trace.jsonl, описанный в README. Переиспользуются: 7.6 (audit log строится на том же формате), 7.10 (healthcheck смотрит в трейсы), 8.2 (скриншоты логов для витрины).

**Темы:**

- Dockerfile для Python-сервиса: базовый образ, копирование кода, установка зависимостей через uv (официальный образ uv или установка одной строкой), точка входа — минимум, без многоступенчатых сборок

## Урок 7.11. Guardrails: атаки на агента и защита до вызова инструмента

**Цель:** ученик умеет защищать агента с доступом к проду не только вычищением данных (7.6), но и слоем guardrails — проверкой входа, выхода и КАЖДОГО вызова инструмента до его выполнения, с журналом решений защиты.
**До урока:** redaction и audit log (7.6), guard.py (5.3), eval-раннер (7.2/7.4). Урок обязательный: у агента есть доступ к прод-ClickHouse — защита от атак не факультатив.
**Темы:**
- карта атак на агента: prompt injection во входе пользователя, инъекция через результат инструмента (tool-result injection: инструкция лежит в данных из SQL или документа RAG), увод агента на несогласованный инструмент, выманивание системного промта
- принцип «policy before tool call»: каждый вызов инструмента проходит проверку ДО выполнения — allow/deny-решение по правилам (какие инструменты, какие аргументы, какие пороги), а не после
- слои защиты: правила в guard.py (детерминированные) → фильтр-классификатор → рубрика в эвалах; ни один слой не «магическая стена», защита — это бутерброд
- LlamaFirewall (Meta, открытый, локальный) как пример готового фильтра входа/выхода/вызовов — разобрать устройство, решить, что взять, а что закрывают свои правила
- adversarial-задачи в golden set: атаки как постоянная часть эвалов — регрессия защиты ловится так же, как регрессия качества
**Материалы:** NirDiamant/agents-towards-production, туториалы agent-security-with-llamafirewall (4 ноутбука: от «hello» до полной обвязки; примеры на OpenAI — переносим на свой стек); наработки 6.8 и 7.6; объяснение репетитора. Для желающих глубже — там же agent-security-apex (red-teaming своего агента, карточка практики).
**Ход сессии:**
1. Разбор карты атак; на схеме архитектуры 7.7 отметить все входы, через которые в агента попадает чужой текст.
2. Ученик расширяет guard.py: функция check_tool_call(tool, args) — allow/deny до выполнения (правила: только известные инструменты, пороги ширины запроса, запрещённые шаблоны в аргументах), решение пишется в audit.jsonl с причиной.
3. Разбор туториала llamafirewall: ученик прогоняет детектор инъекций на своих примерах и решает, где он дополняет правила, а где избыточен.
4. Ученик добавляет в golden_set.jsonl 5–7 adversarial-задач: инъекция во входе, инструкция в результате SQL, инструкция в документе RAG, попытка широкой выгрузки, попытка увести на несуществующий инструмент.
5. Прогон eval-раннера по блоку атак; красная команда: репетитор придумывает новую атаку не из набора — разбор, почему прошла/не прошла.
**Задание:** check_tool_call в guard.py с тестами; 5–7 adversarial-задач в golden set; прогон атак включён в smoke-подмножество CI; в runbook.md — сценарий «подозрение на инъекцию».
**Артефакт:** guard.py с policy-слоем + adversarial-блок golden set + записи allow/deny в audit.jsonl. Переиспользуются: ch-mcp и помощник (общий guard.py), 8.1 (кейс «безопасность агента» — редкий и сильный пункт), карточка практики про red-teaming.
**Критерий готовности:** все 5–7 атак из golden set проходят через eval-раннер и защита срабатывает; опасный вызов инструмента блокируется ДО выполнения (в audit.jsonl видно deny с причиной, SQL не выполнился); ученик объясняет Клоду разницу между redaction (7.6) и policy before tool call.
