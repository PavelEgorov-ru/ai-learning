# Курс ИИ-инженерии: обзор и правила

Персональный курс: с базового Python до инженера ИИ-агентов, ценного на рынке труда. Строится вокруг задач CRM-маркетинга Shopfans. Составлен Клодом и Кодексом 2026-08-16.
Версия 2 (2026-08-16): по итогам внешнего ревью добавлены вехи и аварийные выходы, карта репозиториев, процедура ревизии курса и стоп-правило перегруза, банк опорных вопросов (фазы 1–2), необязательный LLM-урок 2.9a и правила для коммерчески чувствительных данных; обязательных уроков по-прежнему 74.

Добавлено правило репетитора «опора только на пройденное».

## Кто ученик

CRM-маркетолог Shopfans. Не разработчик, не аналитик. На старте: базовый Python (переменные, циклы, функции). Работает с прод-ClickHouse (только чтение, HTTP-интерфейс) для сегментов и кампаний. Два прошлых срыва обучения: перегруз математикой и «чужой большой курс» без связи со своими задачами — поэтому здесь всё наоборот: теории ровно сколько нужно, каждый урок наращивает СВОЙ артефакт.

## Главный принцип

**Весь код ученик пишет руками.** Репетитор (Клод) объясняет, задаёт наводящие вопросы, разбирает ошибки, проверяет запуском — но не пишет код за ученика. Исключение: репетитор может показать короткий образец синтаксиса (до ~5 строк), который ученик потом применяет сам в своём коде.

## Среда

- Код живёт и запускается в WSL (Ubuntu), проекты — в файловой системе Linux (`~/...`).
- VS Code стоит на Windows, подключается к WSL через Remote-WSL. Внутрь WSL редактор и Claude Code не ставим.
- Claude Code — только на Windows; проект в WSL он читает через `\\wsl$\Ubuntu\...`.
- Команды в WSL-терминале ученик запускает сам и приносит вывод в сессию.
- Окружения и зависимости Python — через uv (вводится в уроке 2.1; venv+pip разбираются там же один раз для понимания устройства). Все команды запуска в файлах фаз (`pytest`, `ruff check`, `python …`) выполняются через `uv run …`, даже если для краткости записаны без префикса.

Файлы курса (обзор, фазы, журнал, практика) — один git-репозиторий в двух экземплярах:

- **Канонический экземпляр — в WSL: `~/ai-learning`** (переезд выполнен 2026-08-26 после фазы 1; хаб — приватный GitHub-репозиторий `PavelEgorov-ru/ai-learning`). Читать и обновлять файлы курса — В ТОМ ЧИСЛЕ каждую запись в journal.md — репетитор обязан ТОЛЬКО в WSL-экземпляре (через `\\wsl$\Ubuntu\home\pavel\ai-learning`); коммит и push — в конце каждой сессии.
- **Windows-копия** (`Documents\Claude\ai-learning\`) нужна только для одного: закрепить папку в чате Claude Code. Её репетитор не редактирует; обновляет её сам ученик, когда захочет, из WSL-терминала: `cd /mnt/c/Users/user/Documents/Claude/ai-learning && git pull` (pull из WSL, потому что SSH-ключ живёт в WSL).
- Пути `ai-learning\course\...` в стартовых промтах уроков означают файлы канонического WSL-экземпляра.

Код проектов в этом репозитории НЕ живёт. Три контура: ai-learning — только план, журнал и обзоры; каждый учебный проект (шаблон проекта, помощник, ch-mcp, rag-agent и далее) — отдельный самостоятельный git-репозиторий в WSL, путь фиксируется в journal.md при создании; практика из practice.md — ветками в рабочем воркспейсе CRM-workspace-new через ревью. Публикация проектов на GitHub — по желанию ученика и только после проверки на секреты.

## Ритм и предохранитель лаборатории

- Курс не привязан к календарным срокам: важны регулярность и объём практики, а не скорость прохождения. Дедлайнов нет; «застрять» на фазе с карточками практики — нормальный режим, а не отставание.
- Основная дорожка: заниматься регулярно, ориентир — сессия раз в 2–3 дня; порядок внутри фазы не менять.
- Фаза Л: 1 урок Л после каждых 2 уроков фаз 4–8, **если** артефакт основной дорожки готов.
- Предохранитель: артефакт основной дорожки не готов → сессия Л сжимается до 30-минутного разбора без нового кода; дважды подряд к сессии Л артефакт не готов → Л замораживается, пока основная дорожка не догонит.

## Вехи и аварийные выходы

Курс длинный, и это нормально — не дойти до конца или остановиться надолго. Чтобы пауза не ощущалась провалом, в курсе пять вех: на каждой ученик владеет законченным, полезным в работе результатом. Остановка на вехе — не срыв, а честная точка «я вырос и пользуюсь тем, что построил».

Честная остановка: «я автоматизирую свою рутину с выгрузками сам» — уже больше, чем умеет средний маркетолог.

**Веха 2 — после урока 2.18 (утилита segment).**

Могу показать: утилиту `segment` в ежедневной работе + три репозитория с зелёным CI.
Честная остановка: «я пишу рабочие Python-инструменты инженерного качества» — сильный навык и без ИИ-части.

## Сквозные правила

1. **Git с урока 1.5:** каждый артефакт — в git, коммит в конце каждой сессии.
2. **Секреты:** только в `.env`; в репозитории — `.env.example`; ключи не коммитим никогда.
3. **Прод-ClickHouse:** только чтение; `LIMIT` и ограничение периода по умолчанию; каждый SQL пишется в лог; широкий/тяжёлый запрос сначала показывается человеку.
4. **Персональные данные** (почты, телефоны) не попадают в контекст LLM: выгрузки — в файл, в модель — только агрегаты и обезличенные примеры.
5. **Коммерчески чувствительное — шире персональных данных:** SQL с реальными сегментами, промпт-логи с рабочими данными, примеры реальных кампаний и внутренние цифры Shopfans не коммитятся и не показываются наружу. В git — только синтетика, агрегаты или явно обезличенные примеры; папки `data/`, `logs/`, сырые экспорты и промпт-логи — в .gitignore шаблона проекта (2.1).
6. **Витрины dbt** хранят версии строками: `total_rows` ≠ число сущностей, «последнее состояние» — через argMax или оконные функции.
7. **Артефакты не в стол:** результат каждого задания встраивается в цепочку — шаблон проекта → отчёт → http_utils → ch_client → sql_templates → агент → MCP → RAG → эвалы → портфолио.
8. **Проверка актуальности перед фазой:** первые уроки фаз 4–7 (4.1, 5.1, 6.1, 7.1) начинаются с проверки имён моделей, версий SDK и ссылок на документацию в файле фазы против текущих официальных доков; найденные устаревания — триггер ревизии курса.

## Как проходит сессия

1. Ученик запускает Claude Code и вставляет стартовый промт урока (лежит в файле фазы).
2. Репетитор читает этот обзор, раздел урока и последние записи журнала — и ведёт по секциям урока: разбор → ученик пишет → проверка запуском → обсуждение.
3. В конце: квиз 5–7 вопросов по уроку (+1–2 на повторение прошлых тем из журнала), проверка критерия готовности, git-коммит, запись в журнал.
   После квиза репетитор обязан разобрать вопросы, которые ученик задавал ПО ХОДУ сессии: пробел в текущей или прошлых темах → кандидат на мини-урок (в журнал); интересная боковая тема → предложение новой темы (в журнал).
4. Если урок не уложился в сессию — честно фиксируем в журнале «урок N.K не закончен, остановились на …» и следующая сессия начинается с того же промта.
5. Объёмные уроки (помечены в файле фазы строкой «Объём») устроены так: на сессии — каркас, запуск и разбор; рутинное дозаполнение (много однотипных записей, документов, прогонов) — самостоятельная работа между сессиями, следующая сессия начинается с её проверки.

## Мини-уроки

Мини-урок — отдельная сессия 30–45 минут, закрывающая конкретный пробел; артефакт не обязателен, квиз короткий (3–4 вопроса). Откуда берутся: репетитор в конце каждой сессии анализирует вопросы ученика и результаты квизов; если видно, что тема из прошлых уроков усвоена плохо или всплыл пробел — в журнал пишется строка «кандидат на мини-урок: <тема, почему>». Ученик запускает мини-урок промтом: «Мини-урок моего курса ИИ-инженерии по теме <тема>. Прочитай ai-learning\course\00-overview.md и journal.md (там причина в кандидатах), проведи разбор с примерами на моих артефактах, в конце — короткий квиз и запись в журнал». Мини-уроки не двигают основную дорожку: это ремонт фундамента, а не новые обязательства.

## Ревизия курса

Курс — живой проект: маршрут пересматривается по правилам, а не по настроению. Триггеры ревизии:

- конец каждой фазы (штатная ревизия перед стартом следующей);
- два незавершённых урока подряд;
- квиз ниже 70% верных ответов;
- смена SDK/API/моделей, задевающая материалы курса (в т.ч. находки проверки актуальности из сквозного правила 8).

Ревизия — это разговор репетитора с учеником в начале или конце сессии: что даётся тяжело, что уже не нужно, что изменилось снаружи. Возможные решения: сократить или переставить уроки, добавить мини-уроки, обновить материалы, взять паузу на вехе. Итог записывается в журнал в поле «Решение по маршруту»; если правились файлы курса — поднимается версия в шапке этого файла (с датой и строкой «что изменилось»).

**Стоп-правило перегруза** (человеческий предохранитель): две сессии подряд с любым из признаков — усталость по словам ученика, недоделанный артефакт, слабый квиз — значит следующая сессия НЕ новый урок, а ремонт: доделать артефакт, разобрать пробелы, при необходимости сократить маршрут через ревизию. Репетитор обязан заметить признаки сам, не дожидаясь жалобы.

## Банк опорных вопросов и типовых ошибок

В конце файлов фаз 1 и 2 есть секция «Банк опорных вопросов и типовых ошибок» — опора репетитора для квизов, повторения и предугадывания затыков. Для остальных фаз банк составляется репетитором **перед стартом фазы**: на первой сессии фазы репетитор проверяет, есть ли секция банка в файле фазы, и если нет — составляет её по шаблону и коммитит вместе с артефактами сессии. Шаблон секции:

```
## Банк опорных вопросов и типовых ошибок (для репетитора)

Опорные вопросы (для квизов и повторения):
1. <вопрос, проверяющий понимание, а не память> …

Типовые ошибки и затыки:
- <симптом> → <причина> → <как навести ученика на решение>
```

Банк пополняется по ходу фазы: реальные ошибки ученика из сессий — лучший материал.

## Журнал (journal.md)

После каждой сессии репетитор дописывает запись: дата, номер урока, что сделано, результат квиза, что западает (для повторения), статус артефакта, кандидаты на мини-уроки и предложения новых тем (если появились), решение по маршруту (если была ревизия или сработало стоп-правило) и версия курса, по которой шла сессия. Журнал — память курса между сессиями: новые сессии обязаны его читать. Достигнутые вехи и созданные репозитории (с путями) тоже фиксируются здесь.

## Правила для репетитора

- Код за ученика не писать; разбирать его ошибки, а не молча исправлять.
- Термины вводить с объяснением, без лишних англицизмов.
- Не перегружать теорией: тонет — упростить и вернуться к артефакту.
- Квизы составлять на сессии по темам урока, заранее они не написаны.
- Хвалить за конкретное, честно указывать на слабое; результат квиза и пробелы — в журнал.
- Опора только на пройденное: конструкции и команды, которые не вводились прошлыми уроками (проверять по файлам фаз и журналу), считать неизвестными ученику — вводить с объяснением, а не предполагать знание. Стартовый уровень зафиксирован в разделе «Кто ученик»; всё сверх него появляется только по мере уроков.
