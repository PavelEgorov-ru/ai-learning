# Фаза 8. Портфолио (2 урока + 1 по желанию)

Цель фазы: превратить три рабочих проекта курса в готовые к показу кейсы, по которым нанимающий инженер за 10 минут поймёт уровень ученика. Сначала собирается локальная витрина; публикация и любые remote-действия выполняются только по отдельному явному разрешению.
На выходе ученик умеет: описывать проект по схеме «проблема → подход → архитектура → тесты/эвалы → ограничения», готовить репозиторий к чужим глазам и показывать работу агента коротким demo-сценарием.
Главный артефакт: локальная витрина с тремя оформленными кейсами — помощник CRM-маркетолога (4.9), ch-mcp (5.5), RAG-агент (6.9) — и demo-сценарием к каждому. По явному разрешению та же проверенная витрина публикуется в профиле GitHub.
Переиспользуется дальше: портфолио — основа резюме и собеседований; схема кейса — шаблон для описания будущих рабочих проектов.

## Урок 8.1. Кейсы проектов

**Цель:** ученик пишет для каждого из трёх проектов кейс по схеме «проблема → подход → архитектура → тесты/эвалы → ограничения».
**До урока:** помощник v1.0 (4.9), ch-mcp v1.0 (5.5), RAG-агент v1.0 (6.9); черновики кейсов `docs/case-draft.md` из уроков 4.9, 5.5 и 6.9 под рукой — кейсы собираются из них, а не с нуля; результаты эвалов и сводные таблицы фаз 6–7 под рукой.
**Темы:**
- схема кейса: проблема (чья боль и цифры «до»), подход (почему так, какие варианты отброшены), архитектура (компоненты и поток данных, схема текстом или mermaid), тесты/эвалы (что и как проверялось, цифры), ограничения (что агент не умеет и когда ему нельзя доверять)
- честность как козырь: раздел «ограничения» отличает инженера от продавца; протокол атаки из 6.8 — материал, а не позор
- санитизация: секреты, персональные данные клиентов и внутренние цифры Shopfans не попадают ни в локальный пакет для передачи, ни в публичный кейс; примеры заменяются синтетическими, а допустимость агрегатов согласуется отдельно
- язык кейса: писать для нанимающего инженера — конкретика вместо лозунгов, цифры вместо «значительно улучшил»
**Материалы:** объяснение репетитора.
**Ход сессии:** 1) разбор схемы кейса на примере помощника: устно проговорить все пять разделов; 2) ученик пишет CASE.md помощника целиком, включая архитектурную схему; 3) проверка: Клод в роли нанимающего инженера читает кейс и задаёт вопросы — правки по итогам; 4) ученик размечает каркасы CASE.md для ch-mcp и RAG-агента (все пять разделов с тезисами); 5) обсуждение: какие цифры из эвалов и таблиц notes.md подтянуть в каждый кейс.
**Задание:** дописать все три `CASE.md` до полного вида по схеме; в кейс RAG-агента включить таблицу прогресса качества из 6.7 и выводы эксперимента с внедрением из 6.8; проверить каждый кейс на секреты, персональные данные и внутренние цифры перед локальной передачей или публикацией. Commit выполняется только по явному запросу.
**Артефакт:** три CASE.md в репозиториях помощника, ch-mcp и rag-agent — ядро витрины 8.2 и заготовка ответов на собеседовании.
**Критерий готовности:** Клод в роли нанимающего инженера по каждому кейсу отвечает на три вопроса: какую проблему решает, как устроен, где его предел — только из текста кейса, без доступа к коду; секретов и персональных данных в текстах нет.
**Промт для старта сессии:**
```
Начинаем урок 8.1 моего курса ИИ-инженерии.
Прочитай:
1. ai-learning\course\00-overview.md — правила курса;
2. ai-learning\course\phase-8-portfolio.md — раздел урока 8.1;
3. ai-learning\course\journal.md — последние записи.
Веди сессию по файлу урока: разбор темы → я пишу код руками в WSL → проверяем запуском. Код за меня не пиши — подсказки, наводящие вопросы, разбор моих ошибок. В конце проверяем критерий на моей самостоятельной работе и реальном запуске, разбираем механизм и граничный случай, фиксируем результат и пробелы в журнале. Процентных квизов нет. Commit, push и публикация — только по моему явному запросу. Служебные свидетельства готовит преподаватель.
Фокус урока: кейсы трёх проектов (помощник 4.9, ch-mcp 5.5, RAG-агент 6.9) по схеме «проблема → подход → архитектура → тесты/эвалы → ограничения». Главное — написать кейс помощника целиком, выдержать проверку тобой в роли нанимающего инженера и не пустить в тексты секреты и персональные данные.
```

## Урок 8.2. Витрина: локальный пакет, GitHub и demo-сценарии

**Цель:** ученик собирает локальную витрину: порядок в трёх проектах, общий индекс и воспроизводимый demo-сценарий для каждого. После отдельного явного разрешения локальная витрина переносится в профиль GitHub: README профиля, описания и закреплённые проекты.
**До урока:** три `CASE.md` из 8.1 готовы и проверены локально; commit или публикация не являются prerequisite.
**Темы:**
- гигиена локального проекта: README с назначением и запуском, ссылка на `CASE.md`, актуальный `.env.example`; бейдж удалённого CI добавляется только если такой прогон действительно разрешён и выполнен
- локальный индекс портфолио: кто, что умеет, три проекта и пути к кейсам; по отдельному разрешению он становится README профиля GitHub со ссылками
- demo-сценарий: воспроизводимый показ на 3–5 минут — команды по шагам, ожидаемый вывод, скриншоты или фрагменты JSONL-логов (санитизированные)
- порядок материалов: что рекрутёр видит в первые 30 секунд локально; закреплённые GitHub-репозитории настраиваются только после явного разрешения
- проверка чужими глазами: прогон demo-сценария строго по тексту, без знаний автора
**Материалы:** объяснение репетитора.
**Ход сессии:** 1) разбор: путь рекрутёра по локальному пакету — от общего индекса до demo; 2) ученик наводит порядок в трёх локальных проектах (README и ссылки на кейсы) и пишет общий индекс портфолио; 3) ученик пишет `DEMO.md` для помощника и прогоняет его строго по тексту в чистой сессии терминала; 4) репетитор в роли постороннего проверяет, понятна ли витрина и выполним ли сценарий; 5) только после явного разрешения ученик добавляет GitHub-описания, темы, README профиля и закреплённые проекты. Без разрешения обсуждает, как сослаться на локальный пакет или передать его адресату приватно.
**Задание:** `DEMO.md` для всех трёх проектов, каждый прогнан по шагам от чистого запуска; скриншоты/фрагменты логов добавлены и очищены от секретов, персональных данных и внутренних цифр; общий локальный индекс ведёт к каждому кейсу и demo. Если публикация отдельно разрешена, перенести проверенные материалы в GitHub и закрепить три репозитория; без разрешения remote и push не выполнять.
**Артефакт:** локальная витрина — общий индекс и три проекта с `CASE.md` и `DEMO.md`; по явному разрешению — профиль GitHub с тем же содержанием и закреплёнными проектами.
**Критерий готовности:** репетитор в роли рекрутёра проходит локальную витрину и по каждому проекту называет назначение и путь запуска demo; ученик воспроизводит demo-сценарий помощника с чистого терминала без подглядывания в код. GitHub проверяется только если публикация была явно разрешена и реально выполнена.
**Промт для старта сессии:**
```
Начинаем урок 8.2 моего курса ИИ-инженерии.
Прочитай:
1. ai-learning\course\00-overview.md — правила курса;
2. ai-learning\course\phase-8-portfolio.md — раздел урока 8.2;
3. ai-learning\course\journal.md — последние записи.
Веди сессию по файлу урока: разбор темы → я пишу код руками в WSL → проверяем запуском. Код за меня не пиши — подсказки, наводящие вопросы, разбор моих ошибок. В конце проверяем критерий на моей самостоятельной работе и реальном запуске, разбираем механизм и граничный случай, фиксируем результат и пробелы в журнале. Процентных квизов нет. Commit, push и публикация — только по моему явному запросу. Служебные свидетельства готовит преподаватель.
Фокус урока: локальная витрина — общий индекс, порядок в трёх проектах и воспроизводимые demo-сценарии со скриншотами/логами. GitHub, remote, push и закрепление проектов — только по моему явному запросу; локального результата достаточно для зачёта.
```

## Урок 8.3 (по желанию). Показ наружу: HTTP-интерфейс и развёртывание

Урок необязательный: основной курс закончен на 8.2. Браться, когда портфолио готово и хочется поднять его рыночную читаемость — «сервис доступен не только на моей машине».

**Цель:** ученик оборачивает помощника в простой HTTP-интерфейс и проверяет локальный защищённый demo. Развёртывание вне машины и публичная ссылка — отдельное продолжение только по явному разрешению.
**До урока:** помощник упакован (7.8), Dockerfile есть (7.9), витрина 8.2 готова.
**Темы:**
- варианты показа: воспроизводимый локальный запуск или запись demo как базовый результат; публичная ссылка как условное продолжение после оценки рисков и явного разрешения
- минимальный HTTP-интерфейс поверх помощника: один-два маршрута (задать вопрос, проверка живости) — FastAPI как самый короткий путь
- защита: токен доступа в заголовке (из `.env`), ограничение частоты запросов, потолок стоимости; эти ограждения проверяются локально до любого внешнего доступа
- условное развёртывание: только после явного разрешения контейнер из 7.9 переносится на выбранный хостинг; секреты задаются переменными окружения хостинга, а не входят в образ
- что НЕ выставлять: прод-ClickHouse наружу не смотрит — публичная версия работает на обезличенной копии данных или заглушках; это ограничение честно описывается в demo
**Материалы:** объяснение репетитора; документация FastAPI (fastapi.tiangolo.com) — раздел First Steps; NirDiamant/agents-towards-production, туториал fastapi-agent — агент за HTTP с авторизацией по заголовку, SSE-стримингом и готовыми pytest-тестами, полностью самодостаточен (агент-заглушка, ключи не нужны) — хороший образец до написания своего; документация выбранного хостинга.
**Ход сессии:**
1. Разбор: что меняется, когда сервис доступен снаружи — угрозы, стоимость и данные; решение о внешнем развёртывании пока не принимается автоматически.
2. Ученик пишет `api.py`: маршрут вопроса и маршрут живости (healthcheck из 7.10 переиспользуется), токен из `.env`.
3. Ученик добавляет ограничение частоты и дневной потолок стоимости (счётчик поверх трейсов 7.5).
4. Локальная проверка на loopback: валидный/невалидный токен, rate limit, потолок стоимости, обезличенная заглушка вместо production-данных. Это полный локальный результат урока.
5. Только после явного разрешения: выбрать хостинг, развернуть контейнер, задать секреты через переменные окружения, проверить ссылку с чужого устройства и добавить её в опубликованную витрину.
**Задание:** `api.py` с токеном, ограничением частоты и потолком стоимости; локальный сервис отвечает только на обезличенных данных/заглушках, а тесты доказывают отказ без токена и срабатывание лимитов. Если внешнее развёртывание отдельно разрешено, опубликовать тот же проверенный контейнер и добавить ссылку в витрину 8.2; без разрешения сохранить локальный demo-сценарий и санитизированную запись показа.
**Артефакт:** `api.py` и воспроизводимый локальный HTTP-demo; по явному разрешению — развёрнутое demo по ссылке. Переиспользуется в резюме и откликах как инструкция или запись, а при разрешённой публикации — как живой demo.
**Критерий готовности:** локальный запрос с валидным токеном возвращает ответ помощника, без токена — отказ; rate limit и потолок стоимости проверены; в demo нет production-данных и секретов. Публичная ссылка и проверка с чужого устройства требуются только если ученик явно разрешил развёртывание.
**Промт для старта сессии:**

Прочитай:

Веди сессию по файлу урока: разбор темы → я пишу код руками в WSL → проверяем запуском. Код за меня не пиши — подсказки, наводящие вопросы, разбор моих ошибок. В конце проверяем критерий на моей самостоятельной работе и реальном запуске, разбираем механизм и граничный случай, фиксируем результат и пробелы в журнале. Процентных квизов нет. Commit, push и публикация — только по моему явному запросу. Служебные свидетельства готовит преподаватель.
