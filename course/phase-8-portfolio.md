# Фаза 8. Портфолио (2 урока + 1 по желанию)

Цель фазы: превратить три рабочих проекта курса в публичные кейсы, по которым нанимающий инженер за 10 минут поймёт уровень ученика.
На выходе ученик умеет: описывать проект по схеме «проблема → подход → архитектура → тесты/эвалы → ограничения», готовить репозиторий к чужим глазам и показывать работу агента коротким demo-сценарием.
Главный артефакт: профиль GitHub с тремя оформленными кейсами — помощник CRM-маркетолога (4.9), ch-mcp (5.5), RAG-агент (6.9) — и demo-сценарием к каждому.
Переиспользуется дальше: портфолио — основа резюме и собеседований; схема кейса — шаблон для описания будущих рабочих проектов.

## Урок 8.1. Кейсы проектов

**Цель:** ученик пишет для каждого из трёх проектов кейс по схеме «проблема → подход → архитектура → тесты/эвалы → ограничения».
**До урока:** помощник v1.0 (4.9), ch-mcp v1.0 (5.5), RAG-агент v1.0 (6.9); черновики кейсов `docs/case-draft.md` из уроков 4.9, 5.5 и 6.9 под рукой — кейсы собираются из них, а не с нуля; результаты эвалов и сводные таблицы фаз 6–7 под рукой.
**Темы:**
- схема кейса: проблема (чья боль и цифры «до»), подход (почему так, какие варианты отброшены), архитектура (компоненты и поток данных, схема текстом или mermaid), тесты/эвалы (что и как проверялось, цифры), ограничения (что агент не умеет и когда ему нельзя доверять)
- честность как козырь: раздел «ограничения» отличает инженера от продавца; протокол атаки из 6.8 — материал, а не позор
- санитизация: никакие секреты, персональные данные клиентов и внутренние цифры Shopfans в публичный кейс не попадают — примеры обезличиваются
- язык кейса: писать для нанимающего инженера — конкретика вместо лозунгов, цифры вместо «значительно улучшил»
**Материалы:** объяснение репетитора.
**Ход сессии:** 1) разбор схемы кейса на примере помощника: устно проговорить все пять разделов; 2) ученик пишет CASE.md помощника целиком, включая архитектурную схему; 3) проверка: Клод в роли нанимающего инженера читает кейс и задаёт вопросы — правки по итогам; 4) ученик размечает каркасы CASE.md для ch-mcp и RAG-агента (все пять разделов с тезисами); 5) обсуждение: какие цифры из эвалов и таблиц notes.md подтянуть в каждый кейс.
**Задание:** дописать все три CASE.md до полного вида по схеме; в кейс RAG-агента включить таблицу прогресса качества из 6.7 и выводы эксперимента с внедрением из 6.8; проверить каждый кейс на секреты и персональные данные перед коммитом.
**Артефакт:** три CASE.md в репозиториях помощника, ch-mcp и rag-agent — ядро витрины 8.2 и заготовка ответов на собеседовании.
**Критерий готовности:** Клод в роли нанимающего инженера по каждому кейсу отвечает на три вопроса: какую проблему решает, как устроен, где его предел — только из текста кейса, без доступа к коду; секретов и персональных данных в текстах нет.
**Промт для старта сессии:**
```
Начинаем урок 8.1 моего курса ИИ-инженерии.
Прочитай:
1. ai-learning\course\00-overview.md — правила курса;
2. ai-learning\course\phase-8-portfolio.md — раздел урока 8.1;
3. ai-learning\course\journal.md — последние записи.
Веди сессию по файлу урока: разбор темы → я пишу код руками в WSL → проверяем запуском. Код за меня не пиши — подсказки, наводящие вопросы, разбор моих ошибок. В конце: квиз 5–7 вопросов по уроку (+1–2 на повторение из журнала), проверка критерия готовности, git-коммит артефактов урока, разбор моих вопросов за сессию (пробелы — кандидатами на мини-урок в журнал), запись результата в журнал.
Фокус урока: кейсы трёх проектов (помощник 4.9, ch-mcp 5.5, RAG-агент 6.9) по схеме «проблема → подход → архитектура → тесты/эвалы → ограничения». Главное — написать кейс помощника целиком, выдержать проверку тобой в роли нанимающего инженера и не пустить в тексты секреты и персональные данные.
```

## Урок 8.2. Витрина: GitHub и demo-сценарии

**Цель:** ученик доводит профиль GitHub до состояния витрины: порядок в репозиториях, README профиля, закреплённые проекты и воспроизводимый demo-сценарий для каждого.
**До урока:** три CASE.md из 8.1 закоммичены.
**Темы:**
- гигиена репозитория: README с назначением и запуском, описание и темы репозитория, ссылка на CASE.md, бейдж CI (из 2.17), актуальный .env.example
- README профиля GitHub (репозиторий с именем пользователя): кто, что умеет, три проекта со ссылками
- demo-сценарий: воспроизводимый показ на 3–5 минут — команды по шагам, ожидаемый вывод, скриншоты или фрагменты JSONL-логов (санитизированные)
- закреплённые репозитории и порядок: что рекрутёр видит в первые 30 секунд
- проверка чужими глазами: прогон demo-сценария строго по тексту, без знаний автора
**Материалы:** объяснение репетитора.
**Ход сессии:** 1) разбор: путь рекрутёра по профилю — от README профиля до demo; 2) ученик наводит порядок в трёх репозиториях (README, описания, темы, ссылки на кейсы) и пишет README профиля; 3) ученик пишет DEMO.md для помощника и прогоняет его строго по тексту в чистой сессии терминала; 4) Клод в роли постороннего проверяет: понятен ли профиль и выполним ли сценарий; правки; 5) обсуждение: как ссылаться на портфолио в резюме и что обновлять после фазы 7.
**Задание:** DEMO.md для всех трёх проектов, каждый прогнан по шагам от чистого запуска; скриншоты/фрагменты логов добавлены и вычищены от секретов и персональных данных; три репозитория закреплены в профиле.
**Артефакт:** витрина GitHub — README профиля, три репозитория с CASE.md и DEMO.md, закреплённые проекты; готовая база для резюме и откликов.
**Критерий готовности:** Клод в роли рекрутёра проходит профиль и по каждому проекту называет назначение и путь запуска demo; ученик воспроизводит demo-сценарий помощника с чистого терминала без подглядывания в код.
**Промт для старта сессии:**
```
Начинаем урок 8.2 моего курса ИИ-инженерии.
Прочитай:
1. ai-learning\course\00-overview.md — правила курса;
2. ai-learning\course\phase-8-portfolio.md — раздел урока 8.2;
3. ai-learning\course\journal.md — последние записи.
Веди сессию по файлу урока: разбор темы → я пишу код руками в WSL → проверяем запуском. Код за меня не пиши — подсказки, наводящие вопросы, разбор моих ошибок. В конце: квиз 5–7 вопросов по уроку (+1–2 на повторение из журнала), проверка критерия готовности, git-коммит артефактов урока, разбор моих вопросов за сессию (пробелы — кандидатами на мини-урок в журнал), запись результата в журнал.
Фокус урока: витрина GitHub — README профиля, порядок в трёх репозиториях, закреплённые проекты и воспроизводимые demo-сценарии со скриншотами/логами. Главное — чтобы посторонний человек прошёл профиль и запустил demo без моей помощи.

## Урок 8.3 (по желанию). Показ наружу: HTTP-интерфейс и развёртывание

Урок необязательный: основной курс закончен на 8.2. Браться, когда портфолио готово и хочется поднять его рыночную читаемость — «сервис доступен не только на моей машине».

**Цель:** ученик оборачивает помощника в простой HTTP-интерфейс, защищает его токеном и разворачивает вне своей машины, чтобы demo открывалось по ссылке.
**До урока:** помощник упакован (7.8), Dockerfile есть (7.9), витрина 8.2 готова.
**Темы:**
- зачем показ наружу: рекрутёр, открывающий ссылку, ценнее рекрутёра, читающего инструкцию по установке
- минимальный HTTP-интерфейс поверх помощника: один-два маршрута (задать вопрос, проверка живости) — FastAPI как самый короткий путь
- защита: токен доступа в заголовке (из .env), ограничение частоты запросов, потолок стоимости в день — публичный агент без ограждений быстро съест бюджет
- развёртывание: контейнер из 7.9 на простом хостинге (VPS или платформа с бесплатным уровнем); секреты — переменными окружения хостинга, не в образе
- что НЕ выставлять: прод-ClickHouse наружу не смотрит — публичная версия работает на обезличенной копии данных или заглушках; это ограничение честно описывается в demo
**Материалы:** объяснение репетитора; документация FastAPI (fastapi.tiangolo.com) — раздел First Steps; NirDiamant/agents-towards-production, туториал fastapi-agent — агент за HTTP с авторизацией по заголовку, SSE-стримингом и готовыми pytest-тестами, полностью самодостаточен (агент-заглушка, ключи не нужны) — хороший образец до написания своего; документация выбранного хостинга.
**Ход сессии:**
1. Разбор: что меняется, когда сервис доступен снаружи (угрозы, стоимость, данные); выбор хостинга.
2. Ученик пишет api.py: маршрут вопроса и маршрут живости (healthcheck из 7.10 переиспользуется), токен из .env.
3. Ученик добавляет ограничение частоты и дневной потолок стоимости (счётчик поверх трейсов 7.5).
4. Развёртывание контейнера на хостинг, секреты через переменные окружения; проверка по ссылке с телефона.
5. Обновление витрины: ссылка на живое demo в README профиля и DEMO.md помощника.
**Задание:** api.py с токеном, ограничением частоты и потолком стоимости; сервис развёрнут и отвечает по публичной ссылке на обезличенных данных; ссылка добавлена в витрину 8.2.
**Артефакт:** api.py + развёрнутое demo по ссылке. Переиспользуется: резюме и отклики (живое demo), любой будущий перенос сервисов на сервер.
**Критерий готовности:** запрос по публичной ссылке с валидным токеном возвращает ответ помощника, без токена — отказ; в публичном контуре нет прод-данных и секретов (ученик показывает, откуда берутся данные demo); ссылка работает с чужого устройства.
**Промт для старта сессии:**
```
Начинаем урок 8.3 моего курса ИИ-инженерии (необязательный).
Прочитай:
1. ai-learning\course\00-overview.md — правила курса;
2. ai-learning\course\phase-8-portfolio.md — раздел урока 8.3;
3. ai-learning\course\journal.md — последние записи.
Веди сессию по файлу урока: разбор темы → я пишу код руками в WSL → проверяем запуском. Код за меня не пиши — подсказки, наводящие вопросы, разбор моих ошибок. В конце: квиз 5–7 вопросов по уроку (+1–2 на повторение из журнала), проверка критерия готовности, git-коммит артефактов урока, разбор моих вопросов за сессию (пробелы — кандидатами на мини-урок в журнал), запись результата в журнал.
Фокус урока: HTTP-интерфейс помощника и развёртывание demo по публичной ссылке; главное — токен, ограничение частоты, потолок стоимости и ни капли прод-данных и секретов в публичном контуре.
